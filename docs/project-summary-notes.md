# 当前进展与待办：本次改动与待讨论问题

更新日期：2026-11-23

## 这次完成的部分

这次只增加项目摘要与页面展示，没有修改任务拆解、报告生成、编号校验和执行编排规则。

打开已有项目，标题下面默认展开「当前进展与待办」。用户可以先看当前阶段、这一步的结果、待处理事项和下一步，再阅读下方完整讨论。

- 摘要优先显示当前步骤：执行中、等待确认、部分结果、失败等，不再一直重复项目介绍。
- 对比相邻保存版本，展示需求条目修订、基线确认、退回意见和任务状态变化。
- 显示最近活动时间、最后保存版本和对应阶段，方便分清当前执行与已保存结果。
- 失败时直接显示失败原因，明确旧结果仍保留，不能视为本步骤成功生成的新结果。
- 执行阶段展示任务数量、已验收、待验收、运行、失败和阻塞数量。
- 简版只显示较短文字和前三项待办，点击「展开完整摘要」可以查看完整内容。
- 各角色的同意、有条件同意、不同意分别显示，避免把有条件支持写成全部通过。
- 保留原有确认、退回、验收按钮及详细记录；摘要仅提供指引，不自动代替用户确认。

摘要使用已有数据和程序规则，不增加模型调用。没有新事件或保存变化时保持原状，不为刷新而制造新结论。当前只合并完全相同的待办文本，不宣称能自动识别所有语义重复问题。

## 如何检查

1. 启动工作台，在左侧打开已有项目。
2. 确认标题下显示「当前进展与待办」。
3. 进入不同阶段，观察当前步骤和下一步是否对应实际状态。
4. 退回修改或确认基线后，检查最近保存的变化及版本信息。
5. 对于失败记录，检查摘要是否展示失败原因，而不是把旧规格当成新结果。
6. 内容较长时展开完整摘要，确认末尾内容和全部待办仍在。

最近一轮摘要及页面相关验证为 **13 项通过**，包含现有工作台和排期交互检查。此前初版曾跑过完整测试，但这不代表后续每轮修改都重新跑过完整测试。摘要修改没有额外调用真实模型 API；页面检查使用已有记录和模拟数据。

## 发现的问题：先记录，尚未决定修改

以下问题不属于本次摘要交付范围，没有在业务模块中修复。

### 1. 详细报告生成可能因需求编号不一致失败

本地待办网站案例在确认需求基线后，停在「编写详细需求」，报错为「报告需求编号必须与已确认的需求基线一致」。已有需求和历史记录仍然保留。

源码中，报告阶段会让模型再次输出需求清单，并校验编号集合是否与基线相同。这是排查方向；还应结合失败调用结果，确认具体缺失或多出的编号。

可讨论两种处理方式：加强提示和错误反馈，要求模型保留编号；或者由程序复用已确认清单，让模型只补充报告说明。两者涉及业务流程取舍，应由组内确定。本次保留原校验，没有绕过错误，也没有自动重试付费调用。

### 2. 部分用户决定是否进入后续需求，仍需检查

测试中曾提出「截止日期必填」，后续需求表仍出现「可选或必填待确认」。目前不能仅凭截图判断是操作未正确退回、确认意见没有作为修改处理，还是后续生成未沿用决定。

建议按「填写意见—确认或退回—再次生成」重放一遍，检查决定记录和传入内容，再决定是否调整交互或上下文传递。不能直接将它认定为某个模块的缺陷。

### 3. 重复异议和支持比例的表达可以进一步讨论

不同角色多次提出 Python 环境和本地端口等相近问题，完整记录较长。后续可考虑按问题归并，保留各角色来源。

「支持比例」与「有条件同意」容易被用户理解为同一种通过结论。摘要已分别列出复核意见，但原评分表及支持比例算法保持不变；是否统一修改名称和展示方式，待组内讨论。

### 4. 本地修改后，页面刷新不一定加载新模块

摘要更新过程中出现过刷新后仍显示旧版本，重启工作台后新功能生效。当前使用重启作为处理方法。是否要调整开发时的文件监听和加载方式，需要进一步定位，暂不认定已经解决根因。
